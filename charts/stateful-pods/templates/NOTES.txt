Those names are permanent in the same way. Renaming a volume does not move its data - it
orphans the claim and provisions a new empty one. Its size cannot be changed here either:
a StatefulSet's volume claim templates are immutable once it exists, so growing a volume
means expanding the claim itself, on a StorageClass that allows it.

Whatever the machine's own root filesystem had at one of those paths is hidden while the
volume is mounted, not deleted.
{{- end }}

On its first start the machine's root filesystem is filled from its {{ $machine.source.kind }} source,
once. After that the volume is the machine's operating system and changing the source
changes nothing.

The machine then boots. Watch it, with the kubectl plugin or without:

  kubectl machine console {{ $name }} --namespace {{ $root.Release.Namespace }} --follow
  kubectl --namespace {{ $root.Release.Namespace }} logs {{ $objectName }}-0 --follow

Get a shell in it - this is the machine's own shell, not the chart's:

  kubectl machine shell {{ $name }} --namespace {{ $root.Release.Namespace }}
  kubectl --namespace {{ $root.Release.Namespace }} exec --stdin --tty {{ $objectName }}-0 -- /bin/sh

The plugin addresses this machine as {{ $name }}, the name you declared it under, and
reports which stage it is in while it is being made - which is the one thing the raw
commands above cannot do while the root filesystem is still being seeded:

  kubectl machine status {{ $name }} --namespace {{ $root.Release.Namespace }}

The plugin is at https://github.com/kitsunoff/stateful-pods, and everything above and
below works without it.

The machine reports itself ready when its operating system has finished starting, and its name
resolves before that, so you can reach it while it boots. Deleting the pod asks it to shut
down and waits up to 120 seconds; it is not killed where it stands.

The chart writes /etc/hostname, /etc/hosts and /etc/resolv.conf into the machine on every
boot. To keep one of them as the machine's own, create the marker beside it:

  touch /etc/.stateful-pods-ignore.resolv.conf

{{- $provisioning := include "stateful-pods.machine.provisioning.resolved" $ctx | fromYaml }}
{{- $backend := $provisioning.backend }}
{{- if eq $backend "cloud-init" }}

This machine is provisioned by cloud-init. The chart writes a NoCloud seed into it at
/var/lib/cloud/seed/nocloud, hands its host name, host table, resolver and network
configuration back to the layers above, and removes /etc/cloud/cloud-init.disabled - the
marker the distributions ship in their LXC images, without which a seed is read by nothing.

This needs cloud-init IN the machine's root filesystem. If it is not there the machine will
not start, and the provisioning step says so:

  kubectl --namespace {{ $root.Release.Namespace }} logs {{ $objectName }}-0 --container provision

That is deliberate. A machine seeded and never read would boot with no users, no keys and
no way in, which looks exactly like a successful install. For an image without cloud-init -
`void-current` among the presets, because its upstream publishes no cloud variant - set
machines.{{ $name }}.guest.provisioning: exec and then delete the pod, because a
StatefulSet does not replace a pod that never became ready.
{{- else }}
{{- $execJob := include "stateful-pods.machine.exec.jobName" $ctx }}
{{- if include "stateful-pods.machine.exec.hasScript" $ctx }}

This machine is provisioned by its own script, run inside it once it has finished booting.
Nothing is written into it before that: the script needs the machine's shell, its init and
its package manager, and none of those exist until the machine is up.

The script is carried by a Job beside this pod, which is where its output is:

  kubectl --namespace {{ $root.Release.Namespace }} logs job/{{ $execJob }} --follow

This install did not wait for it unless it was given `--wait --wait-for-jobs`: `--wait` alone waits
for workloads and not for Jobs, so a release can report success while its machine is still being
configured.

That Job holds a ServiceAccount of its own that may get this machine's pod and exec into it,
and reach nothing else in the namespace. That permission is root inside this machine.

The Job's name carries a digest of what it runs, so changing the script creates a new one and
leaving it alone creates none. Changing it does NOT restart the machine. To run the same
script again - after restoring this machine's volume, say:

  kubectl --namespace {{ $root.Release.Namespace }} delete job {{ $execJob }}
  helm upgrade {{ $root.Release.Name }} ...

Removing the script removes the Job and undoes nothing inside the machine. The volume is the
machine.
{{- else }}

This machine is provisioned by exec and supplies no script, so nothing is written into it
beyond the three files above and no Job is rendered for it. It boots with the accounts and
identity its source shipped, so getting in means `kubectl machine shell` until something
inside it is configured to allow anything else.

To configure it from here, set machines.{{ $name }}.exec.script - it runs inside the machine,
as its own root, once the machine is up.
{{- end }}
{{- end }}

A NetworkPolicy is enforced by the cluster's network plugin and by nothing else. If this cluster
runs one that implements no policy, the object above exists and restricts nothing:

  kubectl --namespace {{ $root.Release.Namespace }} get networkpolicy {{ $objectName }}

`kubectl exec` and this machine's readiness are unaffected either way. Both go through the container
runtime rather than over the network, so a machine that admits nothing still becomes ready and can
still be logged into.
{{- end }}

Every decision it makes is a line on the proxy's own output, allowed and refused alike:

  kubectl --namespace {{ $root.Release.Namespace }} logs {{ $objectName }}-0 --container envoy

That is where "why can this machine not reach X" is answered. Nothing has to be turned on.

The pod's own resolver is allowed without a rule, because a rule written as a name needs one.
IPv6 is not proxied and is dropped outright. A process inside the machine running as user 1337 is
exempt from the redirect, which is why a policy worth relying on has a rule matching an address.
